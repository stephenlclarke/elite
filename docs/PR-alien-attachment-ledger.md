# Define scalable physical alien attachments and independent stat folding

AlienAttachmentLedger is a separate owner-bound value ledger with no fixed bay, item, receipt or per-hull gameplay count cap. Each physical module uses its trusted acquisition command UUID as its item UUID, plus an attachment address containing the actual hull UUID and that item UUID. Multiple identical module types remain distinct. Normal inventory unique-fitting rules are untouched. Relocation, storage and whole-hull transfer preserve item, source and irreversible contribution. Retirement retains the complete record and source proof permanently rather than reopening acquisition.

AlienModuleDefinition describes four stable IDs: alien-module-energyCapacity, alien-module-energyRecharge, alien-module-shieldCapacity and alien-module-shieldRecharge. Every unmodified physical instance contributes 1,000 basis points, or 10% of the resolved normal base. These source contracts require an actual structured SalvageLot with matching non-null loot evidence and alien provenance, correct identity, content, condition, quality, scalar axes, declared mass and extents. The project source defaults are 8 kg and half-extents (2,2,2). Legacy artefacts, research flags, ordinary technology and human-provenance lots do not match. The physical source's selected scalar axis is nil; its fixed bonus is 1,000 regardless of quality. The distinct typed IDs must be routed to this ledger, rather than ordinary capped scalar fitting.

Upgrade sources use the corresponding alien-module-upgrade- ID, a matching selected axis and quality increments of 500, 1,000 or 1,500 basis points. These are project balance choices. Each consumed upgrade remains attached as a full permanent source receipt and adds to that physical item's persisted contribution, independent of normal grades, promotion or terminal caps. A source cannot be consumed for a second item, after hull transfer, or after retirement. Complete source lots are saved once in their physical item or upgrade receipt; permanent typed commands reference identities. The version-1 ledger rejects unknown schema versions. The derived source-claim cache is reconstructed on decode. Duplicate physical/command keys are rejected before decoding their payload, saved commands must retain their matching source records, and saved contribution must exactly match all retained upgrades. No archive eviction or unchecked Sendable conformance is introduced.

AlienAttachmentEffects folds only actually fitted records on the supplied active hull. It reports each type's physical count and aggregate percentage, then applies four independent additive multipliers to already resolved ordinary base values once. Shield capacity and recharge affect their corresponding front/rear values. Stored, retired and inactive-hull modules contribute nothing. A subsequent ordinary upgrade changes the base without changing alien identities or receipts. The EMP energy-module count is the physical fitted count of energy-capacity plus energy-recharge modules; a larger upgraded percentage does not count as another physical module. Integer and floating-point representability failures refuse without truncation or clamping; they are not fixed gameplay pool limits. Resolving statistics never refills current energy or shields.

## Central integration contract

Coder 1 owns actual alien loot generation, source admission, salvage collection and source consumption. This source contract is not a producer or proof of a real salvage event. The actual actor must bind trusted command IDs and exact owner/revision/item/hull context, validate the source is currently owned and unconsumed, copy source and attachment state, consume one real source and publish both candidates durably or neither. Fitting must revalidate the current authenticated PLUGH main-station docking proof and real hull ownership; these pure relocation helpers cannot supply that authority. Shops, service costs, current resource clamping and all source/runtime/UI flows remain central integration work.

Register the new physical and upgrade IDs with real profiles and definitions, while preventing generic scalar-fit paths from consuming them into normal component caps. The ordinary equipment inventory is not their physical owner. Commander/save integration must preserve the separate ledger, validate ownership, reject unsupported downgrade fields and retain all source history. Existing effective ShipPerformance/NPC resource numeric caps must not become hidden alien stack limits; distinguish validated native input bounds from finite effective runtime statistics. Global JSON preflight and save-file byte bounds may require scalable chunking: the new ledger's large roundtrip regression does not establish unlimited whole-app saving. Runtime/readout integration must pass the ordinary base before alien folding, display each actual installed type's count and total percentage, and use the returned physical energy count for EMP separately from ordinary grade depth.

## Validation and limits

Regression source covers 2,050 distinct fitted modules and a ledger roundtrip beyond the old 256/2,048 pools, independent repeated types, stored/inactive exclusion, changed normal bases, all quality upgrades, identity-preserving transfer/storage/reload, retired and cross-item source replay refusal, wrong owner/revision/command/axis/provenance, legacy artefact refusal, duplicate poisoned keys, missing source proof, saved contribution downgrade and numeric overflow refusal. These are pure source/ledger/effects tests, not actual loot, PLUGH, cash, fitting, ship transfer or native gameplay acceptance.

Only strict Swift formatting lint, scoped Markdown lint and whitespace checks ran. No compiler, typecheck, tests, native process, media generation, CI or publishing ran. Source and regressions remain uncompiled and unexecuted. All changes are new files; no Commander, Game, ordinary inventory, salvage producer, actor, shop, renderer or save container was edited. See [motivation](ISSUE-alien-attachment-ledger.md).

Source validation now rejects section indices outside the existing salvage contract before admitting either a module or upgrade. Negative tests change source and command identity evidence consistently for sections 64 and 65,535, checking acquisition, upgrade and saved-state refusal without mutation. During decoding, the final command join reuses the unique validated receipt-operation index rather than searching an item's entire upgrade history for every command. A 1,025-upgrade single-item roundtrip and orphan-upgrade command refusal regression cover this path; no timing or execution claim is made.
