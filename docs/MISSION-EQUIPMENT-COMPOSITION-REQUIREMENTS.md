## Exact issue and ownership boundary

`Sources/EliteCore/EquipmentMutations.swift` central `grantMissionEquipment` is insufficient for scripted `gear.issue`: its underlying grant can return when the same device is fitted, reuse a held personal device, or generate a random UUID. Script issue requires the declared quantity of newly issued physical items with deterministic original UUIDs. Do not attach an obligation to an invented identity or appropriate a paid spare. Provide an explicit canonical admission result using caller-supplied identities and mission/resource provenance, with no paid prerequisite history fabricated. Preserve the existing legacy grant policy separately.

Mission `ScriptEquipment.swift` issues held items by default. Explicit fitting must either fit every requested item under the actual hull constraints or reject the whole candidate transaction. Return requires the original unconsumed identities; an all-items policy refuses consumed originals, whereas remaining-items policy permits recorded actual consumption. Release removes the outstanding loan obligation while retaining the physical items and their source. Item/source/issue/consumed/returned references must validate in both directions, including missing-content saves. Staging both physical inventory and mission ledger must complete before full candidate validity/publication.

Every actual canonical consumer must respect those obligations: shop/replacement, fitting/storage, reward/grant, legacy mission removal, hull transfer and consumable use. Distinguish an absent device, where a legacy removal may be a no-op, from blocked or invalid custody, which must reject its transaction. `consumeEquipped` currently collapses throwing removal failures to false and cannot serve as the only authoritative mission transaction result. Define whether modification of a loan is permitted before implementing that path; upgrades must not erase its identity, recovered provenance or outstanding return obligation.

## Standard round identity prerequisite

Use the canonical inventory for standard finite loaded missile rounds, with actual hull pylon locations. The compatibility missile count reflects fitted rounds. Once-only versioned migration may convert legacy count N into N stable round identities; an explicitly empty migrated inventory must remain empty. Held rounds, fitting and firing preserve the original identity. Admission/removal, launched projectile source, mission consumption receipt and ordinary native effects publish together, or all roll back. Virtual unlimited shots must not fabricate consumption of a real loaned round. No automatic refill, missile variants or additional structural pylons are introduced by this prerequisite.

The canonical256-item capacity includes physical rounds. Validate real hull capacity, pylon bounds and duplicate identities; reject unsupported/overflowing migration while preserving the original save. The previous Mission bag's10000-item limit cannot justify silently discarding items to fit the canonical inventory.

## Accepted mission-side consumer baseline

After G02 owner handback, Mission runtime is locally accepted at `d12311d8fca20277aefc150f487acafb7377b0e4`; subsequent Researcher commits are documentation only. Mission Coder1 is mapping actual consumers and migration ambiguities while the central owner prepares a pinned concrete contract. This section is source-only compatibility review, not a competing API or permission to implement before agreement.

`ScriptTransactions.GameRuntime.writeCommander` selects `ScriptSaveStore` when any instance, owned berth, old equipment bag, contract board or trial exists. That store requires a native calendar ledger and writes Commander, mission, world and contract chunks before publishing a format21 pointer. Canonical adoption has a different persisted inventory field and may exist without active missions. The contract must specify whether canonical inventory presence alone promotes an ordinary save, how the required calendar ledger is prepared at an authorized mutation boundary, and how native central saves/world state remain compatible. Merely renaming the predicate or letting a decoder drop an unrecognized field is insufficient. Missionless, empty adopted inventory and missing-content outstanding-loan fixtures are distinct required cases.

Mission `Game.fireMissile` currently selects the original fitted highest-count pylon item, uses its native legacy combat branch, then records actual consumption. The inspected central `d896f02` implementation first calls `launchGameplayMissile`, then debits the compatibility count only after admission succeeds. Compose obligation settlement into the actual canonical launch transaction; do not restore the older combat implementation over the central path. `EquipmentFitting.recordOwnedGearConsumption` updates the issuer/resource consumed set and emits `gear.consumed`. Both must refer to the physically consumed original, and rejected launch/save must preserve all of them together.

Mission `PackTransactions.Commander.apply` currently refuses legacy `equipmentRemove` when its fitted device is an outstanding loan. The canonical bridge must preserve that refusal and use the throwing actual removal result; generic name-set deletion cannot release or consume a foreign loan. Current hull transfer retains every original item, refits compatible equipment, stores leftovers, preserves occupied berths and refuses cargo/fuel overflow. Canonical transfer must preserve those mission obligations alongside its stronger intrinsic statistics, provenance and hull binding.

The accepted old bag allows held items with condition0...10000 and bounded modifications, although fitting requires condition10000 and no modifications. Therefore valid legacy stored equipment is not necessarily a pristine stock item. Reject unsupported mapping without altering the original save, or agree an explicit lossless retained metadata representation. The canonical contract must also state its outstanding-loan modification policy; current mission primitives support store/refit/return/release and consumption, but do not establish a graded loan-upgrade feature.
