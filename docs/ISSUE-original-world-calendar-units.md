# Calendar distance applies BBC scaling to native light-years

Full CI 683 on `1f9098a910aefa17655f3aeadbb59df03257b64e` recorded deadline-proof failures in the procurement container cases. The installed human-approved `l337-world-1` catalogue stores Cartesian Double coordinates in light-years. Its authenticated SHA256 is `120543eedc02a705cce0e37d026125bf926ec22651cff9337ca5d943f2ffd99d`. Native flight and route enumeration use those coordinates directly, but `scriptCalendarDistance` still halves Y, truncates the square root and multiplies by 0.4, the conversion selected for the replaced BBC byte-coordinate universe.

This understates elapsed journey time. With a seven-LY cap and at most three hops, applying that conversion to already-LY coordinates makes the existing 48/72-hour unavailable-route witnesses impossible. Independent catalogue arithmetic finds all 49 origin-zero routes below 57,673 seconds under the old scaled calendar; actual Cartesian journey costs range from 35,798 to 494,106 seconds including the existing 600-second launch charges. No random seed, route pool or deadline should be altered to conceal that unit mismatch.

Use native Cartesian distance for calendar charging while retaining the quadratic journey policy, 600-second launch charge, admission, cancellation, inclusive deadlines, resource accounting and once-only settlement. The original-world migration explicitly excludes predecessor world aliases and old-save compatibility. Historical BBC route fixtures therefore need a separately reviewed provenance update; changing their literals is not part of this product repair. See [the proposal](PR-original-world-calendar-units.md).
