## Frozen terms and proposed lifecycle

| Difficulty | Base reward | Acceptance-relative duration | Variants |
| --- | --- | --- | --- |
| 1 | 500 CR | 172800 game seconds | Encrypted data, sealed package |
| 2 | 750 CR | 172800 game seconds | Encrypted data, sealed package |
| 3 | 1000 CR | 259200 game seconds | Encrypted data, sealed package |

Reward is `(base + 300 * frozen shortest-route hops) * 10` integer decicredits. Data uses zero tonnes; the protected package uses exactly one tonne. There is one unique item per accepted offer, no deposit, failure fee, encounter bonus or mission kill payment. Independent native bounties remain independent.

Proposed project policy: one authored provider, one shared exclusive group `g02-courier` across stations, variants and difficulties. Generate six rows in order `data-1`, `package-1`, `data-2`, `package-2`, `data-3`, `package-3`. Each row draws its own destination; equal destinations across rows are allowed. An active or suspended job blocks another acceptance from this provider, including when its content is missing. Terminal jobs retain receipts but release exclusivity. Decline consumes that row for the saved epoch; completion, failure and abandonment consume the accepted row permanently. Another row or a later epoch has another offer/item identity. No terminal item can be resurrected.

Use the existing station/content board cache, offer UUID namespace, job identity, quotes and painted-control proof. Proposed refresh period is 3600 seconds of the new menu-excluding clock described below. Reopening does not refresh within an epoch. A stale review must return to a newly painted board before acceptance. Refresh cannot alter an accepted job. If no route candidate exists, return a clear unavailable result without a board or RNG mutation; native refuelling/refitting may make the first generation possible in that same epoch. Once any six-offer snapshot is published, changes to fuel, fit, completion or reopening never regenerate that snapshot. Rows with insufficient present fit, reach or deadline feasibility remain visible and disabled with a native reason; no usable offer means no acceptance. An all-disabled six-row board is still frozen until its next normal epoch, with no immediate refresh/retry draw. A scarce candidate set still generates six draws and permits repeated destinations; do not fill disabled rows by sampling again.

## Shortest routes and deterministic generation

Add a bounded, pure route planner for this profile rather than using the weighted `NavigationGraph.path`. Its inputs are the actual current chart, ordinary systems, accepted native jump/tank limits and actual current fuel, captured with the generation proof. Support charts 0 through 7, systems 0 through 255, actual main orbital origin/destination only. Exclude synthetic Plugh, secondary stations, inter-chart travel and same-system delivery.

Proposed project route policy: FIFO breadth-first search, neighbours ascending by stable system ID, maximum depth three. An edge uses `StarSystem.distance(to:)`. Use the actual accepted `Commander.jumpCap`, `Commander.maximumJumpDistance` and `Commander.fuelCapacity` getters with current native fit validity. The first edge must satisfy actual `maximumJumpDistance`; later edges may use `min(jumpCap, Double(fuelCapacity) / 10)` assuming an ordinary station refuel. Do not substitute an intrinsic-only range rule that ignores accepted fitted reach. It selects the lexicographically first minimum-hop path for ties. Candidate destination IDs are sorted ascending after the search. The plan stores the full origin-through-destination path, native edge distances and generation reach inputs. Current fuel is not silently replaced with full fuel; later refuelling is an explicit assumption, costs the player's actual money and is never granted by the mission. Affordability of every future refuel is not guaranteed by the quote.

No additional navigation computer is required by the profile. Source evidence: `FuelStorage.swift` defines `jumpCap` as `max(performance.jump, navigationTier?.jumpCap ?? 0)`; `NavigationComputer.swift` derives `navigationTier` from equipment names. Native fitted extensions affect those accepted getters; removing a navigation/fuel extension must affect current feasibility through the same getters. These are not a verified dynamic health projection. G1's later equipment source exposes fitted navigation/statistics APIs, but Orchestrator confirms it has no dynamic navigation HP/healthy-extension API and it is not this accepted base. Its salvage condition affects initial earned bonuses, not current device health. Future G1 earned fitted reach/spool/fuel-cost helpers and any separately owned later health model remain pending owner-reviewed composition dependencies. Do not call absent APIs, add a G02 health subsystem, inspect derelict hull energy as device health, advertise health-aware reach or claim damage-health tests. Validate the commander through existing fit invariants; no mission-only equipment repair, loan or virtual capacity. Unlimited-fuel mode is not a generation input that substitutes for actual fuel; a real native refill already reflected in commander fuel can affect a later first generation or acceptance. Unlimited cargo does not create physical mission hold.

Freeze `reachRuleRevision = "elite-880d3a-native-reach-v1"` with its actual native input values: hull/performance identity, accepted navigation tier and fuel-storage count, current fuel, computed jump cap, maximum jump distance and tank capacity. Revalidate the frozen proof against that revision's formula, while rechecking current travel through the accepted current getters. A later G1 composition must explicitly map its new reach/spool/fuel-cost rule revision without rewriting any accepted destination, route, reward, deadline or custody. This revision binding is source provenance, not a second reach implementation or permission for G02 to integrate equipment.

At confirmation, recheck the frozen first edge against actual fuel and every remaining edge against the current fitted cap/tank, plus real hold. Do not pick another route. An accepted route is the frozen quote/reward basis, not a mandatory tour: delivery requires the actual destination, item and contact. Alternative native travel is allowed and cannot change the reward. After acceptance, a hull/equipment change may make that advisory route temporarily infeasible; retain the item and deadline, show a refit/refuel warning and let the player recover through native actions. Hull change still must fit all held mission cargo and passengers, with no free missiles or item replacement.

Three hops alone do not establish deadline feasibility: a native seven-light-year calendar journey can already consume roughly 49 hours before launch/flight. For the quoted station-refuel itinerary, freeze each edge's existing `scriptCalendarDistance(to:)`, its native `distance * distance * 3600` journey seconds, and one 600-second launch per leg (origin and each assumed intermediate main-station stop). Store `calendarLowerBoundSeconds = sum(journeySeconds) + 600 * hopCount` with the terms. This is a lower bound for that stated itinerary because manoeuvring, spool/flight and any future timed service add time; it is not a global optimum over every alternative travel strategy.

Proposed strict-margin project policy: the frozen row is usable only if its independently revalidated native itinerary lower bound is strictly less than its fixed difficulty duration. A bound equal to or greater than the duration disables the row with its cost and reason. Equality-safe actual handoff remains unchanged; this admission margin merely avoids advertising a route with no time left for real flight. Show both the lower-bound duration and the remaining lower-bound headroom, explicitly without a delivery guarantee. Recompute and compare the saved bound at quote, confirmation and load against the frozen path/native calendar formula, and reject mismatched proof. Also revalidate actual reach, fit, clock capacity and the strict margin at confirmation. Do not filter candidates by deadline, change the six draw sequence, reroute, reroll, extend 48/72-hour terms or change hop rewards. Alternative actual travel is allowed after acceptance and cannot change these frozen terms.

Use the existing board hash-derived UInt64 seed as input to a separate native G02 generator. Its initial UInt32 is the low 32 bits, mapping zero to `0x6D2B79F5`. Store generator revision 1, initial/final UInt32 state and each row's pre/post state and selected index. For each of the six rows, advance exactly once with wrapping UInt32 operations:

```text
state ^= state << 13
state ^= state >> 17
state ^= state << 5
unit = Double(state) / 4294967296.0
index = floor(unit * Double(candidateCount))
```

Persist the sorted candidate IDs and canonical routes in the board's generation proof, bounded to 255 destinations and four IDs per route. Native generation constructs the terms/proof; the authored generator receives a read-only plan and supplies the six bounded descriptions. Reject a missing/extra row, changed terms, substituted destination, route, identity or draw. Existing providers retain their LCG. Initial seed, all draws, paths, IDs and terms are frozen, including after content absence. Saved proofs can be structurally and algorithmically revalidated from their frozen inputs without requiring the old hull still to be fitted.

## Proposed typed boundary

Add `courier-contracts-basic-v2` and `mission-calendar-v2` only when executable support exists. Keep the current manifest/API generation with optional guarded declarations, subject to owner review. Proposed manifest `courier` fields are `profile = "PROJECT-SPACE-G02-1"`, `generatorRevision = 1`, `deliveryContact = "courier-delivery"` and `abandonContact = "courier-abandon"`. The profile fixes terms; authors cannot override money, hold, clock or loss policy. Proposed contact labels are Courier Receiving Officer at the frozen destination and Courier Dispatch Officer at the frozen origin.

| Native type | Retained purpose |
| --- | --- |
| `ScriptCourierGeneration` | Revision, initial/final state, reach inputs, sorted candidates and routes, six draws |
| `ScriptCourierTerms` | Profile, variant enum, difficulty, frozen route/destination/contact, per-leg calendar cost/lower bound and generation binding |
| `ScriptCourierCustody` | Item UUID, offer/job/content/origin binding, one issue receipt and held/terminal state |
| `ScriptCourierAdmission` | Private unencoded one-action original-confirmation proof, cleared on every exit |
| `ScriptCourierTerminalReceipt` | Delivered, expired, abandoned or native physical loss; original action/event sequence, token/revision/epoch, item, causal clock instant, operation identity and payment binding |
| `ScriptMissionCalendar` | Optional persistent menu-excluding clock projection, origin and last native adjustment binding |
| `ScriptCourierPreview` | Read-only difficulty, variant, route, hold, frozen reward, duration and fit issues for existing quote/UI |

Place optional generation proof on `ScriptContractBoard`, terms on `ScriptContractOffer`, optional deadline policy on `ScriptContractJob`, and optional custody on its `ScriptInstance`. Item ID is a deterministic native namespace of the unique offer/job/profile; it cannot be authored or supplied by a dialogue. Receipts bind provider/version/digest, exact job/item/offer, stations, contact and cause. Keep one issue and at most one terminal receipt per job, within the existing bounded instance budget. Reject exhaustion without evicting evidence.

Proposed authored commands: `courier.issue`, `courier.deliver`, `courier.abandon`. They name their local command receipt only, not arbitrary money, item IDs or timestamps. Issue is legal only inside the native accepted-event admission for that exact frozen offer. Deliver requires the real currently presented `courier-delivery` dialogue, its token/revision, actual destination main orbital, held matching item and native confirmation admission. Proposed abandonment policy is explicit confirmation of `courier-abandon` at the original offering main orbital, using the same native dialogue proof and default Back. Asking for a contact, Back or closing a view is insufficient. Restore exact content before using its authored abandonment contact; native expiry/loss do not require content. Terminal notifications are observers, not authority to issue, deliver or lose items.

Add a private candidate-local `ScriptCourierAdmission`, created only by the actual board/contact confirmation entry point, never from an executing queued event. Pin the original confirmation action identity, exact emitted `mission.accepted`/`dialogue.confirmed` sequence, original painted review token or dialogue token, instance revision, runtime epoch, item/offer/job/content/station binding and `missionCalendar` instant. Before native command execution, require that the currently executing envelope has that exact originally pinned sequence and identity; an older envelope cannot mint a fresh admission by borrowing the current token/time. Retain the relevant proof on issue/terminal receipts, without changing the shared `ScriptEventContext` schema.

The admission exists only during that one synchronous confirmation candidate. Install it before emitting/draining its exact event, clear it on every success/failure exit, and do not encode it or leave it in `pendingEvents`. The existing bounded iterative drain must acknowledge that same event and produce the corresponding issue/delivery/abandon receipt before the native action can publish. If its budget ends first, content suspends, a command is omitted or a different event attempts the operation, roll back the entire action candidate, including its newly queued event and admission. Issue must leave exactly one held item; deliver/abandon must leave the matching terminal receipt/outcome. No recursive interpreter invocation, admission across a later key/frame, resumable pending handoff or deferred backdating is allowed.

Use the G21 pattern of a closed profile command surface. Permit its required journal/milestone/dialogue operations and typed courier operations; reject generic credit changes, protected-payload substitution, arbitrary timers/failure causes and receipt-free `mission.finish`. Acceptance must return with exactly one held native item. Delivery must return with exactly one matching terminal receipt and settlement. Deferred or omitted issue/delivery commands fail the complete proposal rather than leaving a partially accepted or paid job. Shared mission finish/settlement validates the native courier receipt while retaining ordinary objective guards.

Physical custody projects onto one reserved payload key in that same instance with value exactly one while held, zero/absent when terminal. Data has a typed held item and no payload quantity. Enforce both directions: a held package requires its exact projection, and a reserved courier payload cannot exist without its item. Other payloads cannot satisfy delivery. Generic cargo commands cannot mutate the reserved key. Acceptance checks `standardCargoCapacity - cargoTonnes`, including fitted passenger hold and every other protected payload; data accepts with exactly zero spare tonnes. Over-capacity virtual cargo cannot make an otherwise invalid physical fit valid. Existing inventory and hull transfer remain authoritative; no market commodity or second inventory is added.

## Menu-excluding clock, equality and delayed events

Source evidence requires an additive clock: existing `calendarActive` advances docked status/market/equipment menus, and existing tests deliberately expect docked status time to advance. Existing contract success requires `< deadline`; generic timers fire at `<= due`. Changing any of these defaults globally would alter accepted packs.

Propose `ScriptClockDomain.missionCalendar`, backed by optional `ScriptMissionCalendar` in `ScriptEngineState`. First G02 board preparation initializes its value from the existing calendar once; subsequent saves retain it. It advances by the same clamped native simulation delta only during unpaused actual flight simulation with menu screens excluded. Docked menus, Gallery, review/contact pages, pause and unloaded wall time contribute zero. Use an explicit screen predicate, shared by runtime and tests, rather than equating all undocked screens with flight. The existing calendar stays untouched.

The enum case alone grants no access. Manifest validation permits a board using this domain only with a fully validated closed courier declaration and both required capabilities. Repeat that check at board generation, quote/confirmation, mission acceptance, command admission and installed-content load. Persisted missing-content jobs/boards must still have valid frozen courier terms, capabilities/profile binding and inclusive policy; a domain/policy without matching courier evidence is corrupt. Generic `timer.ensure`, ordinary authored boards and unsupported manifests cannot use this domain, including in saved timer state. Reject a `ScriptTimer` with `missionCalendar` outright; courier expiry is native. Keep ordinary timers' `<= due` and ordinary success `< deadline` byte-for-byte in behavior. A bare optional calendar projection may survive historical courier completion/content absence but cannot authorize another pack.

Mirror actual admitted native calendar adjustments into this projection: launch adds the existing 600 seconds once; actual completed hyperspace adds the existing admitted source-distance-squared travel time once. Preserve the existing separation between native fuel distance and O08 calendar distance. Check both clocks against their cap jointly before admitting a launch or reserving travel; frame progression leaves the admitted travel headroom in both clocks. Bind mirrored adjustments to the same native operation ID so duplicate completion cannot double-charge. A failed/repeated launch makes no new charge; failed jump admission creates no reservation/charge; a canceled jump releases its reservation without charging journey seconds; successful arrival consumes its reservation and charges exactly once. Real elapsed spool flight before cancellation still counts as flight, not as a canceled journey charge. Current refuel/market/equipment transactions have no simulated service duration, so charge zero rather than inventing one. Any future timed service must use the same native adjustment hook; adding such a service is outside this packet. All mirrored durations are project timing policy, not evidence of server parity. No wall-clock or load-time catch-up is introduced.

Set job `acceptedAt` and `deadline = acceptedAt + duration` from this clock in the acceptance candidate. Proposed `deadlinePolicy = inclusiveConfirmation` is legal only with validated courier terms. Nil retains all old contracts' exclusive policy. `ScriptContractJob.valid`, snapshots, quote checks, native finish and settlement must use the same policy and clock. Completion at equality succeeds; expiry uses strictly `now > deadline`.

Use a native courier expiry sweep after native clock adjustments and before new courier actions, plus after frame advancement and load. Do not install a generic once timer at the deadline or use floating-point `nextUp` as a workaround. Sweep only active courier custody and atomically settle zero-payment failure with a typed expiration receipt. It must work with missing/suspended content: expiry and native loss are ownership safety rules, not Lua handlers. At equality the job remains held; the next representable native advancement beyond the boundary expires it.

Proposed causal policy: handoff is synchronous within the existing native confirmation command and the original-event admission lifetime above. Capture its clock at actual confirmation, validate custody/location/token there, evaluate `courier.deliver` inline and publish consumption/receipt/payment together before another simulation advancement can interleave. An observer processed later sees the frozen terminal receipt and cannot pay again. A delayed `station.docked`, `dialogue.confirmed` lookalike or timer event is insufficient to complete: at a later clock the expiry sweep wins unless the real confirmation already committed. There is no saved pending handoff reservation that pauses the deadline. A queued event claiming an earlier cause time cannot backdate payment. Validation must cover genuine equality confirmation with later observer processing, a pre-deadline dock followed by a late confirmation, forged/deferred earlier timestamps, an older backlog event trying to borrow a new admission and a drain budget that cannot reach the original event. The receipt's causal time, not a later observer's processing time, records a successful handoff.

## Actual physical loss and failure atomicity

The current successful `Game.escapePod` clears ordinary cargo but preserves scripted protected payloads. There is no ordinary package-jettison transition to reuse. Propose the smallest actual loss integration: successful native escape-pod use destroys the abandoned ship's held physical courier packages, and every actual transition from a live ship to native game-over destroys held physical packages. Source fatal paths include the final energy check in `Game.tick` and early game-over returns in `advanceSolarFlight` for sun/planet impact and cabin overheating. Do not rely solely on the final energy branch. No arbitrary `courier.lose` command or forged actor event is accepted. Mere damage, equipment damage, hull exchange and unsuccessful escape-pod attempts do not destroy an item.

Proposed project policy: encrypted data travels with the commander and survives an actual successful escape pod. Fatal game-over does not create a recoverable digital delivery path; starting/loading a commander keeps the existing native game/save semantics. Do not invent a post-death data recovery feature. Expiry and abandonment terminate either variant. Loss terminates only the affected physical jobs, consumes only their reserved hold and records zero success payment. All unrelated cargo, equipment, passenger custody, native bounties and other mission state remain governed by their existing native action.

For successful escape-pod commands, include native package loss receipts and terminal cleanup in the existing command candidate/publication. Hook immediately after successful native pod admission and before gear-consumption/docking observers can run; do not wait until a later event handler to discover loss. A failed escape-pod publication restores the prior Game and controls through `GameRuntime.key`; no half-used pod, lost package or fabricated loss receipt remains. An unsuccessful native pod action creates no loss admission.

For fatal simulation, use one real transition barrier in `GameRuntime.advance`: capture whether the ship was live before tick, keep script events deferred during physical tick, and immediately after tick record loss if it is now game-over, before location observation, any handler drain, save publisher or possible handoff. This covers energy, solar/planet impact, overheating and early returns through the actual native screen transition; it requires no edits to solar physics. Do not let the barrier invoke Lua or rollback physical state. Mark each affected held physical custody with a bounded native pending loss fact immediately. While pending, its one-tonne protected projection remains reserved and delivery is forbidden. Only a successful terminal-resolution candidate removes that exact reserved projection, clears pending status and publishes the zero-payment loss receipt/outcome. No unrelated payload cleanup is permitted.

Publication failure retains the dead ship and pending loss fact in memory for retry, while leaving the previous durable generation intact. Retry native resolution before any further courier action/save and after advancement/load, independently of content/suspension. A valid loaded pending fact cannot be delivered; a loaded fatal physical state with an inconsistent still-deliverable package is rejected, not repaired with an invented event. Never undo a real death or claim an unpublished loss survived a process restart. Persisted pending facts must validate operation/item/origin and held projection, cannot be script-created and must resolve before delivery after load. Fatal data receives no success receipt; existing native reset/load semantics remain in force. No content callback is needed for loss or cleanup.

Acceptance publishes offer consumption, job, frozen clock/policy, issue receipt, item and physical projection in one existing save generation. Handoff publishes exact contact confirmation, item consumption, terminal receipt, mission outcome and native wallet payment in one generation. Failure/abandonment similarly publish only owned cleanup and zero-payment settlement. Save failure restores the previous command state, including the presented review/handoff, without duplicate IDs or payment. Physical simulation follows the separate fact-first rule above. No alternate save controller, wallet, finance ledger or equipment subsystem is introduced.
