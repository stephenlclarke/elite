## Further evidence and concrete native gap

A second first-hand [2008 Elite Plus play report](https://groups.google.com/g/alt.fan.elite/c/NByAWyDtm_U), followed through its11 April update, describes replaying an old save and reaching later missions after fewer than40 jumps. The author explicitly disputes a universal64-jump interval and reports missions did not require one per galaxy. This supports retaining uncertainty about the scheduler, not selecting40 as a recovered constant. The quoted hex-offset list is hearsay within that discussion; neither it nor the author's statements establish executable predicates or C07 combat parameters. The report also describes missing a mission briefing, a reason for the adaptation to retain its destination in the mission journal.

Native source inspection against G02 runtime `42ceeef6e0052cd42ec0f7df000c9f3c0513eb2e` establishes a narrower combat gap. `ScriptNPCDefinition` declares missile stock and encounter construction copies it to the actual body. However, `ScriptNPCWeapons.advanceScriptGun` implements laser or plasma weapons and does not debit that stock. `NavalCombat.navalTactics` excludes bodies with `scriptNPC != nil`. Consequently a profiled C07 Viper with `missiles = 1` does not establish a working finite guided missile. A native launch/consumption/identity/save/ECM contract is required; an unlimited plasma weapon cannot substitute for the declared single missile. This finding is about this inspected engine version, not Elite Plus's historical implementation.

The inspected SH136 file's game profile has energy180, recharge2, speed29.257, acceleration12, pitch/yaw1.8, roll1.4, missiles1 and fuel70. These are common project player-refit values; its catalogue geometry is Oolite-derived. They do not prove the original stolen craft's combat fit. The scripted NPC profile has no independent shield field, so copying SH136's player shield255 into narrative does not make an NPC shield mechanic available. The final handoff must state actual durability behavior explicitly and keep any derived NPC values labelled project estimates.

Existing `ScriptOwnedActor` persistence retains native identity, body condition, missile count, orientation and profiled NPC state. Encounter restoration preserves those fields and creates only a new scene integer ID. Its admitted actors are projected from a main-station reference frame. This is usable persistence foundation, but it does not supply the required first-arrival entry-relative binding or an NPC hyperspace escape policy. The implementation must distinguish living actor unload/cull from proven destruction; missing rendered bodies are never kill proof.

## Proposed project decisions for the next design review

These proposals remain unassigned and do not amend `PROJECT-PCPLUS-C07-v1` or claim historical recovery. Freeze a versioned adaptation before coding. Non-player destruction should terminate the unique-target hunt with zero mission payment, a native cause receipt and no respawn. Refusal leaves an offer available; accepted abandonment or either destruction terminal outcome should prevent reissuing the same historical mission to that commander. Success should require actual player-attributed destruction followed by one issuer-station handoff, with no invented deadline.

Player departure should snapshot the living target's exact native state and preserve it for subsequent admission in the frozen target system. Genuine native target escape, if implemented, should retain the same original identity and spent stock. No departure, reload, trial restart within an ongoing trial, or content recovery may silently heal/refill an existing mission instance. Explicit fresh isolated Gallery restart creates a fresh trial commander and is a separate action. Define relocation for an actor outside the loaded bubble before approving code; preserve its condition and resources, and label any entry-placement rule as a project choice. Do not describe an unimplemented target hyperjump as an existing fact.

The acceptance destination selector also needs an actual reachability audit on all ordinary charts. `(issuer_system + 17) % 256` alone does not prove that the destination is reachable with the permitted native jump graph. If a fallback is necessary, specify and version its deterministic ordering, frozen destination and offer-disable behavior before implementation; do not silently change the retained v1 selector. Final Gallery and contract/journal presentation must expose the same actual named target and issuer, including after reload.

## Destination audit result

The source-transcribed static [route audit](c07-route-reachability-audit.json) finds70 unreachable issuer/target pairs among2048 possible offers at a full-tank seven-light-year jump cap with arbitrary refuelled legs. Human-numbered galaxies3,4,6,7 and8 contain4,4,8,52 and2 failing pairs respectively; galaxies1,2 and5 have none under those assumptions. Every failing pair and component size is retained in the JSON with the immutable `Universe.swift` source hash and derivation. Integer arithmetic reproduces the source distance formula; the Lave seed/name/coordinate sanity anchor agrees. This is a source transcription, not compiled-native parity evidence. Larger navigation ranges, galaxy travel and live first-leg fuel are outside its scope.

This establishes a concrete implementability problem with the retained placeholder selector under standard native travel. Recommended versioned adaptation: retain the preferred+17 target only if reachable under a frozen native reach snapshot; otherwise scan ordinary system IDs cyclically from that preferred target and choose the first other reachable destination. Freeze both selected system and reach/selector revision at acceptance, show the actual named system before confirmation, and disable the offer if there is no reachable other system. Native design review must settle actual first-leg fuel and later station-refuelling assumptions. The v1 research profile remains unchanged until that reviewed version is recorded; no silent fallback is authorized by this audit.
