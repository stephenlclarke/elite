One family owner owns that family's complete per-ID record, geometry, fitting sockets, dimensions, variant details and focused acceptance. Do not assign separate coders to change the stats and mesh of the same ship. Names and capabilities are already resolved in this pack; coders implement the full record rather than independently inventing conflicting values. All unassigned common-file edits go through Root.

## Concrete file layout to agree before coding

Use the repository's existing ship-folder loader and generator where possible. Its eventual canonical source should have one directory per ID, containing the complete TOML, detailed/native design and materials. Do not create a competing runtime catalogue because this design document lives under docs. Root and A record the exact maintained path before family owners start.

Suggested stable resource boundaries, if the current implementation has no equivalent, are `Ships/SHnnn/ship.toml` and `Ships/SHnnn/materials/`; conversions live beneath their parent with an explicit TN ID. Preserve Stephen's one-TOML-per-ship requirement: the maintained TOML contains the specs and the authored detailed/native design, adapting the existing `[design]` and `[nativeDesign]` input. External JSON/binary mesh caches are generated derivatives, not alternative maintained ship definitions. The smaller TOMLs in this documentation pack are implementation contracts; the family owner must merge their decisions with the retained original design arrays into the actual complete maintained ship TOML. Each family owner writes only its ID directories. No family PR edits a shared all-171 Swift array or the mission registry. A owns the minimal typed loader and generated registration; E owns the three exact mission conversion joins. F owns central Markdown/GIF presentation.

The source fingerprint covers TOML, effective geometry, UV/material/texture inputs and relevant renderer version. Derived assets retain their source fingerprints. Renaming one hull must not regenerate unrelated portraits. A shared texture edit declares exactly which hulls use it and invalidates those assets.

## Delivery order and handoff

1. Root records this new design decision and exact track ownership in the authoritative ledger. Reconcile any newer accepted per-hull calibration or in-progress family packet before editing it.
2. A freezes the small typed schema and fixture contract; B/C/D/E can prepare disjoint family records and meshes immediately. A implements actual module/crew/quote effects, not just display fields.
3. Deliver complete families with stats, geometry, tools/crew/access and focused evidence together. Keep unfinished families unavailable with an honest reason; do not use blanket `runtimeReady`.
4. Family owner runs necessary focused unit/component checks and reviews the full change for bugs, performance and style, then follows the current independent review/required PR-check policy. Existing passing evidence is reused when its dependencies are unchanged.
5. F updates the actual quote/help/portrait/GIF row for each admitted family. Visual approval uses the real renderer; source-reference PNGs do not establish runtime acceptance.
6. At a coherent release checkpoint, run the current required broad quality/review/release gates once. Do not infer a new sanitizer policy or start a broad game test campaign from this docs-only pack.

Each handoff identifies base and final commits, exact owned paths/IDs, old/new source hashes, data/geometry/fitting changes, actual executed evidence, review outcome and remaining limitations. Authored tests with no execution are not PASS. A ship drawn in the showroom but not flyable/dockable is not completed.

## Conflict prevention

The `classification` fields partition all 171 base IDs. Capital military exceptions belong only to E, never D. Tithe variants belong only to E and inherit frozen parent performance contracts rather than editing B/C/D's files. F reports data/mesh defects to the family owner and does not silently fix them in generated outputs. Shared save/actor/equipment/mission code is reserved to the named owner before edits. All simulation state stays with GameRuntime and Swift 6 isolation; AppKit remains on the main actor.

No old-format compatibility layer is required. Keep actual owned item/person/blueprint identities and current-format durable state valid while applying a display-name change. Do not use a rename to fabricate discovery, crew, money or equipment.
